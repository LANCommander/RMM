# Battlefield 1942 Windows server: reverse-engineering notes

`BF1942_w32ded.exe` 1.61 (PE timestamp `0x400faa42`, 2004-01-22, image size
`0x39b000`, base `0x400000`, not relocatable). VC++ 7.0, no symbols, RTTI off.
The C++ runtime is `bfcprt.dll` (a renamed msvcp70: `std::basic_string`,
streams) plus `msvcr70.dll`. Every function below was matched against the
named Linux function (see [bf1942-linux.md](bf1942-linux.md)) and its
arguments confirmed from the disassembly. Gamedata: `gamedata/bf1942.ini`
`[windows]` and `[windows_offsets]`.

## Tooling

- Ghidra project `C:\Development\Tools\ghidra-projects\bf1942_w32ded` (the
  exe, fully analysed, plus `RmmPtrFuncs.java`, which creates functions at every
  code pointer in the data sections: 21.5k functions instead of 10.8k).
- `RmmWin.java` (re-work `ghidra-scripts`), driven by
  `re-work\bf1942_win\rw.ps1 <out> <targets>`: decompile by address,
  `str:`/`wstr:` (every function referencing a string), `refs:`, `callers:`,
  `asm:<addr>[:n]`, `calls:` (each call with the callee's `ret n`) and
  `rets:` (the calling convention at a glance). It creates missing functions.
- `re-work\scripts-pe`: `vtmatch.py` (find vtables by the shape of their
  slots, e.g. `0x44=8b41??c3`), `vtfind.py` (the vtable around a function),
  `peimports.py`/`peexports.py`.
- Live server: `re-work\bf1942_win\conctl\conctl.exe <pid> type "<cmd>" | dump |
  peek <addr> [len] [deref]` drives the server console and reads memory;
  `chain.py` follows pointer chains. `deploy.ps1` installs a build into
  `C:\Servers\Battlefield 1942 Server`.

## ABI differences from Linux

- Member functions are `__thiscall` (`this` in ECX, callee pops). RMM's
  detours are `__fastcall` with a dummy EDX parameter, which has the same
  registers and stack layout (`r1_abi.h`).
- Whole-program optimisation changed a few file-local functions:
  `cdKeyAuthorizeCallback` is `__fastcall(gameid, localid | authenticated,
  errmsg, instance)` (`ret 0xc`) and `gcd_getkeyhash` is
  `__fastcall(gameid, localid)`.
- `std::string` is 28 bytes: `+0x4` 16-byte buffer or heap pointer (when
  capacity >= 16), `+0x14` size, `+0x18` capacity (from `bfcprt`'s `c_str` and
  `size`). RMM creates, assigns and destroys engine strings with `bfcprt.dll`'s
  exports (`msvc7_string.cpp`). A string passed by value is copied onto the
  stack and destroyed by the callee; one returned by value goes through a
  hidden pointer pushed after `this`.
- `std::map`/`std::set` objects are `{allocator, header*, size}`. Nodes are
  `{left, parent, right, key @+0xc, value @+0x10, color, isnil}`, and the header's
  parent is the root. `std::list` is `{allocator, header*, size}` with nodes
  `{next, prev, value @+8}`. Gamedata offsets name the container object.
- Vtables: one destructor slot instead of GCC's two, so slots after the
  destructor are 4 lower. Overloads are grouped and sometimes reordered
  (`spawnObject`, `spawnPlayer`), and some classes are laid out completely
  differently (`BFSoldier::getKitId` is `+0x100`, Linux `+0x17c`). No slot is
  assumed; each one used is in `[windows_offsets]`.
- Methods introduced by `GameServer`'s second base get `this` =
  `GameServer + 0x144`: `say`, `getPlayerIPAndPort` and `destroyPlayer`
  (secondary vtable `0x6e6d00`). The primary vtable is `0x6e7048`.

## Loading: `winmm.dll` proxy

The server imports `timeGetTime` from `winmm.dll`, which is not a KnownDLL, so
a `winmm.dll` in the server folder is loaded instead of the system one. The
proxy (`src/loader`) forwards all 193 exports (table generated by
`tools/gen_winmm_proxy.py`) to `%SystemRoot%\SysWOW64\winmm.dll`. In
`DllMain` it patches the exe's entry point with a jump to a stub that
restores it, loads `rmm\bin\rmm.dll` and calls `RMM_Bootstrap`, then jumps to
the real entry point. This runs on the main thread, outside the loader lock,
after `bfcprt.dll` and `msvcr70.dll` are loaded and before the CRT starts.

Why not the launcher: `rmm_launcher.exe`'s remote-thread injection was flagged
by Windows Defender (`Behavior:Win32/DefenseEvasion.A!ml`). Also, the server
restarts itself (`Setup::restartServer`-like `0x00430d00`:
`_spawnl(_P_NOWAIT, "BF1942_w32ded.exe", "+restart 1 +dedicated 1 ...")`
then exit) on `admin.changeMap` and at the end of a map cycle, and the new
process starts without anything injected. The proxy is loaded by every new
process, so RMM is there after a restart with no extra work (verified live).

## Layouts (`[windows_offsets]`)

- **BFPlayer**: name `+0x44` (28-byte string), vehicle `+0x64`, id `+0x70`,
  soldier `+0x98` (`setDefaultVehicle` `0x004045a0`), isAI `+0xa8`, alive
  `+0xa9`, team `+0xac`, kit index `+0xb0` (`changeKit`), deaths `+0xd4`,
  kills `+0xd8`, score `+0xf4`, second score `+0x148` (`scoreEvent`).
- **GameServer**: status `+0x58`, kit map `+0x4c` (as Linux), client map
  `+0x14c`, NetServer `+0x1d8`.
- **Objects**: template `+0x4c`, id `+0x48`, composite parent `+0x50`, all as
  on Linux. `queryInterface` `+0x8`, `queryComponent` `+0x24`,
  `getAbsolutePosition` `+0x34`, `setAbsolutePosition` `+0x38`,
  `getAbsoluteTransformation` `+0x3c` (live BFSoldier vtable `0x006f8870`;
  the engine's FindArmor `0x004508f0` and PCO walk `0x004038c0`). PCO
  `pco_id` `+0x2c`; Armor `getMaxHitPoints` `+0x14`, `getHitPoints` `+0x1c`,
  `isDestroyed` `+0xc8` (all as on Linux). BFSoldier kit id `+0x450`.
- **ObjectTemplate**: `getClassID` `+0xc`, `getName` `+0x14` (as on Linux).
- **ObjectManager** maps: grid `+0x4c`, no-collision grid `+0x64`, PCOs
  `+0x13c`, projectiles `+0x148`, spawners `+0x124`, supply depots `+0x130`,
  registered objects `+0xa0` (`getAllRegisteredObjects`).
- **Soldier items**: item-id vector `+0x3dc`, held slot `+0x3e8`, slot count in
  the soldier template `+0x38c` (Linux `+0x3ac` / `+0x3b8` / `+0x2d4`).
- **ObjectSpawner**: respawn timer `+0x13c`, team `+0x154`. **GameServer**
  spawn timing: waves `+0x299`, delay `+0x29c`, wave interval `+0x2ac`
  (Linux + 0x98, from `killPlayer`), player count `+0x18`.
- **ControlPoint**: template `+0x180`, lose timer `+0x184`, take timer
  `+0x188`, taking team `+0x18c`, team `+0x190`, state `+0x198` (Linux
  `+0x164`..`+0x17c`, from `gotControl`/`lostControl`/`handleFrameUpdate`).
  Template: capture radius `+0x2c8`, take time `+0x2f8`, lose time `+0x2fc`,
  lock byte `+0x304`, only-team `+0x318`, minimum players `+0x308` (Linux
  `+0x1dc`, `+0x1f4`, `+0x1f8`, `+0x200`, `+0x214`, `+0x204`). The class id is
  assumed to be Linux's `0x94a5`, as for soldiers and kits (unverified: an
  empty `rmm cps` would show it's wrong).
- **Bots**: BFPlayer default camera `+0xa4` (`killPlayer`'s `enterVehicle`);
  BotManager bot vector `+0x34`, player-id table `+0x68`; PlayerInput is
  `float[55]` then the 64-bit mask at `+0xe0` (VC++ aligns it to 8), 0xf0
  bytes. BAPAChangeWeapon: Bot info-handle vfunc `+0xcc`, soldier-interface
  item vfunc `+0x18`, action slot `+0x1c`, item `+0x20` (Linux `+0xd0`, `+0x1c`,
  `+0x18`, `+0x1c`).
- **Console access**: `executeLine`'s last flag selects full access (level
  7). At the default level 1 the engine answers getters such as
  `game.serverMaxPlayers` with `Unauthorised method!`, even when they are typed
  at the server console, so RMM passes it (`console_exec_flags = 0x10`).

## Differences from the Linux gamedata

Every Linux feature is ported. Windows doesn't need `getRootParent` (RMM walks the parents) or a separate
`getBotFromPlayerId` (RMM uses `getBot` with the player-id table); see
`[windows] not_used`.
